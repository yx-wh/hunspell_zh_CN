# hunspell_zh_CN

用于中文的 Hunspell 词形表，供[词悦](https://github.com/mumu-lhl/Ciyue/)（Ciyue）和 [次世代GoldenDict](https://github.com/xiaoyifang/goldendict-ng/) 做简繁、异体字，以及**中文与日本新字体（Shinjitai）**的通查。

中文没有词形变化，所以这里的 `st:` 干的是另一件事：记录**哪些字是同一个字的另一种
写法**。词悦会按字读这张表，再组合，因此用一种写法输入的查询，能够命中用另一种写法建立的
词条；GoldenDict-ng 则把「一一对应」的部分交给 OpenCC，这张表只补它补不了的「[一简对多繁](https://ytenx.org/byohlyuk/KienxPyan)」和异体字对应。

本仓库发布的 `zh_CN.dic` 是**精简版**。全量表只是那几本词典词头的派生结果，谁手上有
那些词典都能自己生成；它也没必要全灌进词悦和 GoldenDict-ng——被删掉的那部分，两者都
能自己补上——所以不随仓库发布。既不按字组合、也不走 OpenCC 的读取器（例如闭源专有软件 GoldenDict
Mobile）才需要它，请按下面的「生成」一节自行生成。

## 用法

**词悦**：设置 → Hunspell → 打开「启用词形还原与变体查找」→ 选择包含 `zh_CN.aff` 和
`zh_CN.dic` 的目录导入。

**GoldenDict-ng**：把这两个文件放进 Hunspell 目录，在「词典 → 词典来源 → Hunspell」中
加入该目录并启用。OpenCC 的简繁转换可以同时开启，两者互补。

## `zh_CN.aff`

```text
SET UTF-8
LANG zh
FLAG long
# 空壳
```

没有词缀规则，也没有复合词设置——Hunspell 此时就是一张「写法 → 各种写法」的哈希表，
这正是这里需要的全部。

## 单字条目：繁简双向，冷僻异体单向

繁简、以及辞典里确实用来立目的异体，两个方向都要写：

```text
闲 st:閒    閒 st:闲
适 st:適    適 st:适
㑺 st:俊    俊 st:㑺
```

`闲 st:閒` 只把 `闲` 指向 `閒`，没有 `閒 st:闲`，反向的 `閒适 → 闲适` 就查不到；
`㑺` 在人名里有立目（`刘㑺`），所以输入 `刘俊` 时也要能展开过去。

只被辞典收过一次的冷僻异体则**只写正向**：

```text
𬸕 st:莺    （不写 莺 st:𬸕）
䴏 st:燕    （不写 燕 st:䴏）
```

因为 hunspell 在这里是检索辅助，负责「任意写法都能命中词典」；「某字有哪些
异体」是异体字字典的职责。`莺` 若反向展开到 `𬸕`等字，`莺莺燕燕` 的候选会从
4 涨到 81，多出来的全是查空的。判断标准在 `generate_zh_dic.py` 的
`composes()`：变体必须在多字词头里出现 ≥ 2 次，才保留反向行。

副作用是规范形可能不再单独出现在 `.dic` 里（例如 `spell("燕")` 会是 false）。
但 `燕` 本来就是词典词头，MDX 索引自身能命中；hunspell 在这里只负责补变体，
不承担「这个词存不存在」的判断——因为中文Hunspell只用作简体、繁体、正体、异体转换，不用于拼写检查。

词悦会逐字读这张表并组合，所以对词悦而言，**混写不必进表**：

| 输入 | 展开出的写法（原样 + 5 个） |
| --- | --- |
| `闲适` | `闲适`、`閒適`\*、`閑适`、`閒适`、`闲適`、`閑適` |

\* 来自词级条目，见下。

## 词级条目：逐字转换不够时才写

```text
闲适 st:閒適
```

词级条目**先于**按字组合被读取，所以制表人指定的写法排在前面。它也是表达「非逐字
对应」映射的唯一方式：干/乾/幹、发/髮/發 这类分化，或繁体写法与简体字数不同的词。

单字表里没有的字无法展开——这是这张表的覆盖面边界。

### 一简对多繁：两个「复制」

《汉语大词典》里「复制」其实是两个不相干的词：

- `複製` fù zhì —— 仿造原件、翻印书籍（「不可複製」是禁止拷貝的意思）
- `復制` fù zhì —— 继续控制（《後漢書》《三國志》中的「不可復制」是無法被繼續控制的意思）

简体把它们合成了一个写法。OpenCC 的 `s2t("复制")` 只给 `複製`（常用义），
而 `t2s("複製")` 和 `t2s("復制")` 都给 `复制`——反查时冷僻义会被静默丢掉。

全量表原本有四行，`prune` 按「两个读取器都能自己算出来就删」逐一判定：

| 行 | 词悦逐字组合 | OpenCC | 结果 |
| --- | --- | --- | --- |
| `複製 st:复制` | ✓ | ✓ | 删 |
| `復制 st:复制` | ✓ | ✓ | 删 |
| `复制 st:複製` | ✓ | ✓ | 删 |
| `复制 st:復制` | ✓ | ✗ | **保留** |

所以发布版里只剩一行：

```text
复制/Xx st:復制
```

GoldenDict-ng 靠 OpenCC 拿到 `複製`、靠这一行补上 `復制`；词悦逐字组合
（`复 → 复/複/復`、`制 → 制/製`）本来就能同时展开出两者，实测六种写法里
`複製` 和 `復制` 都在。两个义项都出得来，而表里只存了一条。

## 同一个 head 多行为什么带 `/Xx`

一简对多繁（`发` → `發` / `髮`、`干` → `乾` / `幹` / `榦`）必须写成**同一个
head 的多行**：

```text
发/Xx st:發
发/Xx st:髮
```

`/Xx` 不是词缀规则，`zh_CN.aff` 里也没有定义它。它是用来绕过一个上游 bug 的兼容写法。
必须写成**两字符**：`zh_CN.aff` 用 `FLAG long`，单字符会被 `decode_flags()` 按
`len >>= 1` 截成零长度向量，只靠「指针非空」这个副作用才碰巧生效，而且可能冒
`bad flagvector` 警告；两字符的 `Xx` 是合法 tag，走正规的「有 flag → 不是重复」分支。

Hunspell 1.7.3 的 [`f23fcd33`](https://github.com/hunspell/hunspell/commit/f23fcd33052c7c8a307eaa3e1b1a4c0cdcf45651)
（`ofz: Out-of-memory`）在 `HashMgr::add_word()` 里加了「同 head、无 affix flag
的一律当重复词跳过」的分支，却没比较 `HENTRY_DATA`（morph 描述）。于是
`发 st:發` / `发 st:髮` 两行只留第一行，`髮` 静默消失——`spell("发")` 仍是 true，
所以拼写检查这一侧完全看不出问题。

上游已修：[`cca6830`](https://github.com/hunspell/hunspell/commit/cca68306aedd1a4daea8a5b7d9b9e1886ae71b41)
（2026-11-12，Resolves [hunspell#1171](https://github.com/hunspell/hunspell/issues/1171)）
把判重条件换成 `same_entry_without_flags()`：任一方带 flag 不算重复，双方都无 flag
且 `HENTRY_DATA` 相同才算重复。但它在 v1.7.6 之后 27 个 commit，**尚无任何 release
包含它**，按上游节奏预计从 1.7.7 起。

| hunspell 版本 | 不带旗标的 `发 st:發` / `发 st:髮` | 带 `/Xx` |
|---|---|---|
| ≤ 1.7.2 | 两行都留（`next_homonym`） | 两行都留 |
| 1.7.3 – 1.7.6 | 只剩第一行，`髮` 丢失 | 两行都留 |
| ≥ 含 `cca6830`（1.7.7+） | 两行都留 | 两行都留 |

所以 `/Xx` 是**兼容写法，不是临时补丁**：在新旧库上结果一致，只对 1.7.3–1.7.6 起作用。
截至 2026-11，Debian unstable/testing、Ubuntu 开发版、Fedora 43/44/45、Arch、Homebrew
都还是 1.7.6，删掉会让当前绝大多数用户丢词。

带上任意一个合法 flag 就改回 `next_homonym` 分支；未定义的 flag 不产生派生词形，也不
影响 `spell()`（`hunspell -G` 只会吐出词本身），代价只是多目标行多两个字节。

只有「一个 head 对应多个变体」的行才需要加，单值行不加。两个前提：

- `Xx` 必须在 `.aff` 里**保持未定义**——真给它写 `SFX` 规则就会开始派生词形；
- tag 长度要匹配 `FLAG` 模式：`long` 下必须是两字符（单字符被静默截断），`num` 下
  `Xx` 不是合法 flag，那两行会重新被合并掉。

标准 Hunspell（包括 GoldenDict-ng 用的系统库）都需要这个 flag。词悦自己 vendored
了 `hashmgr.cxx` 并放宽了去重条件，加不加都能拿到全部词干。

**移除条件**：只有当确定不再支持 < 1.7.7 的 hunspell 时才可去掉 `/Xx`。这类非 CVE
修复不会回填到 LTS / 稳定版发行版，1.7.3 这一代按发行版生命周期会用到 2030 年前后。
真要删时，`generate_zh_dic.py` 与 `jp_shinjitai_lib.py` 里的 `HOMONYM_FLAG` 常量要一起
改（F1 并入的条目也走它），再重新生成 `zh_CN.dic`。

## 生成

需要 `pip install opencc-python-reimplemented`，以及 `mdict-utils`（处理 `.mdx`）。

### 0. 从词典目录生成词表

```bash
python3 build_words.py /path/to/词典目录 words.txt
```

扫 `.mdx` / `.dsl` / `.dsl.dz`，过滤掉句子和例句反查类词典，s2t 时保护 `CHAR_FIX`
里的类推简化字。已经有 `words.txt` 就跳过这一步。

### 1. 从词表生成全量表

```bash
python3 generate_zh_dic.py words.txt zh_CN_full.dic
# 可选：补进完全没有立目的生僻异体（只写正向 st:）
python3 generate_zh_dic.py words.txt zh_CN_full.dic /path/to/variants.json
```

`words.txt` 是一行一个词头（来自你实际使用的词典）。脚本用 OpenCC `t2s` 把每个词
归一化到简体，写正向行 `v st:std`；反向行只在 `v` 真的被辞典用来组词时才写
（见「单字条目」一节）。繁简相同的词没有变体，直接跳过。

**这一步会同时**：把「日本新字体→中文」（F1）并入 `zh_CN_full.dic`，并写出
`ja_JP.txt`（中文→新字体，F2；只是完整 `ja_JP.dic` 的一部分，见下）。依赖同目录下的 `jp_shinjitai.json`，
数据缺失时自动跳过、不影响原简繁生成。`jp_shinjitai.json` 由
`build_jp_shinjitai.py` 从 OpenCC 上游表 `opencc_JPShinjitai*.txt` 派生，一般无需手动改。

「多对一」新字体（弁→辩/辨/瓣/办 等）不能做字符级 `st:`（会污染中文搜索，中文本来也有
「弁」），只能走词级；但 OpenCC 的词级表太薄，连 `弁証法` 都没收。要补全：先 `build_words.py`
备好中文词头 `words.txt`，再跑 `python3 expand_jp_words.py`，它分两趟从你手头真实的中日词典补全词级：

- **Case A（日1↔中多）**：扫描中文词头 → `s2t`+`t2jp` 折成日文形式，仅留日文形式真在日文词典里的
  （你是在日文文本里看到这词才查的，所以必须真有这个词），写出 `jp_words_extra.json`，并入 F1/F2。
- **Case B（中1↔日多）**：扫描日文词典词头里**纯汉字**、且含「中1↔日多」字符（历→歴/暦、铺→舖/舗…）
  的词 → `jp2t`+`t2s`，**不要求中文词头在中文辞典**（你是用中文输入法去拼不会念的日文词），写出
  `jp_words_b.json`，仅并入 F2。

两者生成时都由 `jp_shinjitai_lib` 自动并入（Case B 只进 F2，F1 由单字级按字拼出，不入以免膨胀）。

若只想把 F1 增量并入已有的 `zh_CN.dic`、或重新写出 `ja_JP.*` 而不重跑整表生成，用：

```bash
python3 generate_jp_zh.py
```

单字条目不是单独维护的：中文词典的词表本身就收录单字词头，同一套逻辑自然会把
`閒 st:闲` 这类行产出来——而它们正是词悦能按字组合的前提。

#### OpenCC 不认的异体字

`t2s` 只认识它自己的字表。像 `㑺`（`俊` 的异体）、`㮣`（`概` 的异体）这类字，
`t2s` 原样返回，于是 `㑺` 和 `俊` 被当成两个不同的字，一行 `st:` 都不会生成。

补的依据是 ToyMDict 的 [`variants.json`](https://github.com/asgsdbrseg/ToyMDict)
（16,439 字 / 7,654 组），但它的口径是「异体字字典」，连带收通假与古今字，不能直接
灌进 `CHAR_FIX`。筛选标准：

- 只收**扩展区／兼容区 → BMP** 的组；
- 组内必须有一个 BMP 字**真的参与组词**（在词表的多字词头里出现过），用它当规范形；
- 两端都不在现有 `CHAR_FIX` 里，避免链式折叠。

按这个标准收了两批，共 511 对。没收的：

- 541 个整组都是生僻字（`𠌯` / `㒧`），组内找不到规范形，只能人工查书；
- 2,158 个落在 BMP 内部，多为 `人/入`、`一/壹/乙`、`大/太/泰` 这类形近、通假、古今字组，
  折了会把「大」的查询“污染”成「太」「泰」。

补完后，参与组词的字里有 `st:` 映射的比例从 69.6% 升到 76.5%。

#### 完全没有立目的异体字

第四个参数可以传一份异体字表（格式：字 → 该字所在的整组）。脚本会找出
**表里还没有正向行**、且组内有一个 BMP 字确实被辞典用来立目的扩展区异体，
补一条 `异体 st:规范形`，**不写反向行**。当前补进 893 条。

判据用「表里有没有这个字的正向行」而非「在不在词表」，因为只作为单字词头、
但 `t2s` 原样返回的字不会生成任何行。只补扩展区字，BMP 里的 `人/入`、
`大/太` 这类通假组不会被卷进来。

这些字在任何辞典里都没有立目（或只立单字、从不组词），所以只留正向没有损失：
电子书里复制共享到查词软件的生僻字能送到词典条目，而常用字一侧不会多出候选。不传这个
参数时，生成结果与之前完全一致。

### 2. 精简并发布

```bash
python3 prune_zh_dic.py zh_CN_full.dic zh_CN
```

第二条命令写出 `zh_CN.dic` / `zh_CN.aff`，也就是本仓库发布的那一对；`zh_CN_full.*`
留在本地（需要全量表的读取器可以直接用它）。

这一步删掉「两个读取器都能自己算出来」的词级条目：

- 词悦能用单字行逐字重建的；
- OpenCC 本来就会产出的。

其余保留：

```
1,264,295 条  →  35,840 条（33 MB → 约 690 KB，已含 F1 新字体→中文）
  单字行保留    10,565
  词级行保留    24,508
    不能按字生成   1,256   （词悦补不了）
    OpenCC 补不了 23,252   （GoldenDict-ng 补不了）
```

脚本在写文件前会校验「源表每一条仍可推导」，写完后再校验一次输出文件，因此不会在
无声无息中丢掉候选。换 OpenCC 版本后重跑一次即可，几秒完成。

写文件前还会把 `/Xx` 旗标规范化一遍：**同 head 只剩一行的去掉旗标，多行的每行都补上**。
前者只是省字节，后者是真修 bug——Hunspell 只在「双方都无 flag」时才判重，`弁` 那种
四行里只有两行带旗标的，剩下两行会互相吃掉一个（`弁 st:瓣` 静默消失）；规范化后四个
义项都在。这一步是幂等的，也可以单独对已有 `.dic` 跑。

## 日本新字体（新字体 ↔ 中文）

上面的 `zh_CN.dic` 只处理「中文 ↔ 中文」的写法；本仓库另带一份**日本新字体（Shinjitai）**
互通表，覆盖「新字体 ↔ 中文简/繁」两个方向：

| 方向 | 文件 | 形态 | 效果 |
| --- | --- | --- | --- |
| 新字体 → 中文（F1） | `zh_CN.dic`（已并入） | `新字体 st:中文` | 在中文词典里输入 `桜` / `関数`，命中 `櫻` / `函數`（也含简体 `樱` / `函数`） |
| 中文 → 新字体（F2） | `ja_JP.txt` | `中文 st:新字体` | 输入 `函数` / `函數`，命中 `関数` |

> `ja_JP.txt` 只是完整 `ja_JP.dic` 的**一部分**——真正的日文 Hunspell 还包含日文词形还原（如 `走らない → 走る`），需把它并入 [yx-wh/hunspell_ja_JP](https://github.com/yx-wh/hunspell_ja_JP) 之类的完整表。单独测试时，把 `ja_JP.txt` 改名 `ja_JP.dic`，与对方项目的 `ja_JP.aff`（含真正词形还原）同目录后导入即可。

F2 单独成文件，是因为它是「日文 hunspell」视角：head 是中文，target 是日本新字体。与
`zh_CN.dic` 方向相反，互不污染——中文词典查 `佛` 不会无故展开到 `仏`。

### 数据来源与生成

映射来自 OpenCC 的 `JPShinjitaiCharacters` / `JPShinjitaiPhrases`（已存为
`opencc_JPShinjitai*.txt` 作溯源）。`build_jp_shinjitai.py` 读这两份表，用 OpenCC `t2s`
把旧字体再折到简体，派生出 `jp_shinjitai.json`：每个条目同时带 `trad`（繁）与 `simp`（简）
两侧。字符段只收「一新对一旧」的单字；**多对一**（如 `弁` → 辩/辨/瓣/办）不进字符段，
留给词级表按词处理，避免污染逐字查询。

生成由 `generate_zh_dic.py` 内置：跑它就**自动**把 F1 并入 `zh_CN.dic`、并写出 `ja_JP.txt`
（见「生成」一节）。只想增量更新、不重跑整表生成时，用 `generate_jp_zh.py`。

### 几条约定

- **身份跳过**：新字体与简体中文同形（国/体/对…）时，其 `st:繁体` 与 `zh_CN.dic` 既有的
  简繁通查条目完全重复，字符段直接跳过，交给简繁表；`st:简体` 本就是身份映射也略去。
- **`/Xx` 多目标**：一个 head 对应简+繁两个中文形（桜 → 櫻/樱、`関数` → 函數/函数）时，
  同 head 多行带未定义的 `/Xx` 旗标，绕过 Hunspell 1.7.3–1.7.6 的去重 bug（见上；
  上游 `cca6830` 已修，但发行版尚未跟进）。这是 F1（写 zh_CN.dic）侧的约定，与
  `ja_JP.txt` 无关——那边的 flag 由 hunspell_ja_JP 项目自己的脚本决定。
- **F2 双入口**：每个中文形同时给**简体**与**繁体**两个 head（`函数 st:関数`、
  `函數 st:関数`），覆盖「简化字立目」与「繁体立目」辞典，以及不吃 OpenCC 的词悦。
- **与 OpenCC 的关系**：GD-ng 内置的「中日汉字转换」（OpenCC `t2jp`/`jp2t`）已能覆盖
  繁→新字体；但简体→新字体（对→対、函数→関数）和词级替换（函數/函数→関数）OpenCC 一步
  覆盖不到，`ja_JP.txt` 补的就是这部分。词悦没有 OpenCC，全部靠 `.txt`。

### 挂载方式

**词悦**：设置 → Hunspell → 打开「启用词形还原与变体查找」；点「导入」选包含
`.aff`+`.dic` 的文件夹。**`zh_CN` 与 `ja_JP` 可同时导入**，每个源有独立开关与
「两遍查找」选项。查找模式建议选「补充」，这样 `関数` 会展开出 `函數`/`函数`、
`函数` 会展开出 `関数`，与精确词条并列显示。

**GoldenDict-ng**：编辑 → 词典 → 词典来源 → **Morphology**，把 `ja_JP.txt` 改名 `ja_JP.dic`、与对方项目的 `ja_JP.aff` 同目录后加入该目录（同样地，可与 `zh_CN` 的 Morphology 源并存，按词典组分别启用）。也可同时勾选内置的
「中日汉字转换 → Japanese Shinjitai」，两者互补：`ja_JP.txt` 负责 OpenCC 补不到的
简体 head 与词级替换。

## 已知边界

- 只覆盖**单字表里出现过**的字；表里没有的字保持原样，不会自行发明映射。
- 只做**精确查找**：`st:` 映射整词，无法补全尚未输入的字，所以逐键建议不会展开异体。
- 逐字替换要求**字数相同**；字数不同的映射必须写成词级条目。
- 依赖 Hunspell 的 homonym 行为：1.7.3–1.7.6 上「同 head、无 flag」的行会被去重，本表用未定义的 `/Xx` 绕过（上游 `cca6830` 已修，但要等 1.7.7 铺到下游才谈得上移除），见上面的说明。
